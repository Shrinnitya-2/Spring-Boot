1.1 WHAT IS SPRING FRAMEWORK
─────────────────────────────────────────────────────────────────────────────────
Definition:
  Spring Framework is an open-source, lightweight, enterprise-grade Java
  application framework that provides comprehensive infrastructure support
  for developing Java applications.

Core Principles:
  • Inversion of Control (IoC) - Framework controls object creation
  • Dependency Injection (DI) - Objects receive dependencies from outside
  • Aspect-Oriented Programming (AOP) - Cross-cutting concerns separated
  • Convention over Configuration

Internal Working:
  Spring creates an IoC container (ApplicationContext) that manages the
  lifecycle of all Java objects (called "Beans"). Instead of you creating
  objects with "new", Spring creates them, wires them together, and manages
  their lifecycle.

Interview Answer:
  "Spring Framework is a comprehensive programming and configuration model
  for modern Java-based enterprise applications. It uses IoC and DI to
  reduce coupling between components, making applications testable,
  maintainable, and scalable."

Step 11: ResultSet mapped to List<AgencyAcctRouting> entities
Step 12: ModelMapper converts entities to List<AgencyAcctRoutingDTO>
Step 13: Service returns DTOs to Controller
Step 14: Controller wraps in ResponseEntity with HttpStatus.OK
Step 15: Spring serializes to JSON via Jackson
Step 16: Response sent back to client

Filter Layer:
  - Request interception
  - Authentication/Authorization
  - Executes before controllers

Exception Layer:
  - Custom business exceptions

Constants Layer:

3.2 @SpringBootApplication INTERNAL WORKING
─────────────────────────────────────────────────────────────────────────────────

@SpringBootApplication is a meta-annotation combining THREE annotations:

  @SpringBootConfiguration (same as @Configuration)
    → Marks class as source of bean definitions
    → Allows defining @Bean methods

  @EnableAutoConfiguration
    → Triggers Spring Boot's auto-configuration mechanism
    → Reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
    → Conditionally creates beans based on classpath
    → Example: DataSourceAutoConfiguration creates DataSource because
      spring-boot-starter-data-jpa is on classpath

  @ComponentScan
    → Scans base package (com.nw.odAdmin_service) and sub-packages
    → Finds classes annotated with @Component, @Service, @Repository,
      @Controller, @RestController, @Configuration
    → Registers them as beans in ApplicationContext

─────────────────────────────────────────────────────────────────────────────────

@Service is a specialization of @Component:
  1. Component scanning finds @Service classes

  5. Registers in ApplicationContext

5.3 YOUR SERVICE EXAMPLE ANALYSIS
─────────────────────────────────────────────────────────────────────────────────

@Service
public class AgencyAcctRoutingServiceImpl implements AgencyAcctRoutingService {

    @Autowired
    private AgencyAcctRoutingRepo agencyAcctRoutingRepo;
    @Autowired
    private ApplicationUsersRepo applicationUsersRepo;
    @Autowired
    private UsersRepo usersRepo;
    @Autowired
    private ModelMapper mapper;

    @Override
    public AgencyAcctRoutingDTO saveAgentAcctRouting(AgencyAcctRoutingDTO dto) {
        // 1. Validate user exists
        boolean existsUserId = usersRepo.existsByUserId(dto.getUserId());
        if (!existsUserId) {
            dto.setStatus("NOT_FOUND");
            dto.setMessage("User Id is not in the OmniView Users Table.");
            return dto;
        }

        // 2. Check if record already exists
        Optional<AgencyAcctRouting> existing = Optional.ofNullable(
            agencyAcctRoutingRepo.findFirstByAgntNbrAndEntpsId(
                dto.getAgntNbr(), dto.getEntpsId()));

        if (existing.isPresent()) {
            dto.setStatus("EXISTS");
            return dto;
        }

        // 3. Map DTO to Entity and save
        AgencyAcctRouting entity = mapper.map(dto, AgencyAcctRouting.class);
        AgencyAcctRouting saved = agencyAcctRoutingRepo.save(entity);

        // 4. Map Entity back to DTO and return
        AgencyAcctRoutingDTO response = mapper.map(saved, AgencyAcctRoutingDTO.class);
        response.setStatus("CREATED");
        return response;
    }
}

BUSINESS LOGIC FLOW:
  Validate → Check Existence → Transform → Persist → Return Result

5.4 TRANSACTION MANAGEMENT
─────────────────────────────────────────────────────────────────────────────────

@Transactional annotation:
  • Wraps method in database transaction
  • Auto-commits on success
  • Auto-rollbacks on RuntimeException
  • Uses Spring's PlatformTransactionManager

Your project uses @Transactional on repository update methods:
  @Modifying
  @Transactional
  @Query("UPDATE AgencyAcctRouting a SET ... WHERE a.id = :id")
  int updateAgencyAcctRoutingById(...)

Interview Answer:
  "@Transactional creates a proxy around the bean. When a method is called,
  the proxy begins a transaction, executes the method, and commits.
  If a RuntimeException occurs, it rolls back automatically."

6.2 SPRING DATA JPA INTERNAL WORKING
─────────────────────────────────────────────────────────────────────────────────

MAGIC: You write an INTERFACE, Spring creates the IMPLEMENTATION at runtime!

public interface AgencyAcctRoutingRepo extends JpaRepository<AgencyAcctRouting, Long> {
    List<AgencyAcctRouting> findByAgntNbr(String agntNbr);
}

HOW IT WORKS INTERNALLY:
  1. Spring scans for interfaces extending JpaRepository
  2. Creates a JDK dynamic proxy at runtime
  3. Proxy implements ALL methods:
     - Inherited: save(), findAll(), deleteById(), count(), etc.
     - Derived queries: parses method name → generates JPQL
     - @Query methods: uses provided JPQL/native SQL

  findByAgntNbr(String agntNbr) is parsed as:
  → SELECT a FROM AgencyAcctRouting a WHERE a.agntNbr = :agntNbr

  findByAgntNbrAndEntpsId(String agntNbr, String entpsId) is parsed as:
  → SELECT a FROM AgencyAcctRouting a WHERE a.agntNbr = :agntNbr AND a.entpsId = :entpsId

6.3 YOUR REPOSITORY METHODS
─────────────────────────────────────────────────────────────────────────────────

DERIVED QUERY METHODS (auto-generated SQL):
  findByAgntNbrAndEntpsIdAndUserId(...)   → WHERE agntNbr=? AND entpsId=? AND userId=?
  findByAgntNbrAndEntpsId(...)            → WHERE agntNbr=? AND entpsId=?
  findByAgntNbr(...)                      → WHERE agntNbr=?
  findByEntpsId(...)                      → WHERE entpsId=?
  findByUserId(...)                       → WHERE userId=?
  existsByUserId(...)                     → SELECT CASE WHEN COUNT(*)>0 THEN true
  findFirstByAgntNbrAndEntpsId(...)       → WHERE ... FETCH FIRST 1 ROW

CUSTOM @Query METHODS:
  @Modifying @Transactional
  @Query("UPDATE AgencyAcctRouting a SET a.agntNbr = :newAgntNbr, ...")
  int updateAgencyAcctRoutingById(@Param("id") Long id, ...)

  @Query("SELECT a FROM AgencyAcctRouting a WHERE a.agntNbr LIKE :agntNbr")
  List<AgencyAcctRouting> findByAgntNbrLike(@Param("agntNbr") String agntNbr)

6.4 JpaRepository HIERARCHY

7.1 @Entity AND ORM MAPPING
─────────────────────────────────────────────────────────────────────────────────

ORM (Object-Relational Mapping):
  Maps Java objects to database tables. Each entity class = one table.
  Each field = one column. Each instance = one row.

YOUR ENTITY EXAMPLE:

@Entity                                    ← Marks as JPA entity (DB table)
@Table(name = "AGENCY_ACCT_ROUTING")      ← Maps to specific table name
public class AgencyAcctRouting implements Serializable {

    @Id                                    ← Primary key
    @GeneratedValue(strategy = GenerationType.SEQUENCE,
                    generator = "agency_acct_routing_seq")  ← Auto-generate ID
    @SequenceGenerator(
        name = "agency_acct_routing_seq",
        sequenceName = "SEQ_AGENCY_ACCT_ROUTING",
        allocationSize = 1)               ← Oracle sequence for ID generation
    private Long id;

    private String agntNbr;               ← Maps to AGNT_NBR column
    private String entpsId;               ← Maps to ENTPS_ID column
    private String userId;                ← Maps to USER_ID column
}

7.2 ANNOTATION BREAKDOWN
─────────────────────────────────────────────────────────────────────────────────

@Entity     → Tells JPA this class maps to a database table
@Table      → Specifies exact table name (if different from class name)
@Id         → Marks the primary key field
@GeneratedValue → Defines ID generation strategy
@SequenceGenerator → Uses Oracle DB sequence for unique IDs
@Column     → Specifies column name/properties (used in ApplicationUsers)
Serializable → Required for caching and distributed systems

7.3 HIBERNATE ORM MAPPING FLOW

PART 8: DTO LAYER DEEP EXPLANATION
================================================================================

8.1 WHAT IS DTO
─────────────────────────────────────────────────────────────────────────────────

DTO (Data Transfer Object):
  A simple Java object used to transfer data between layers and to/from clients.
  It acts as a contract between the API and the client.

8.2 WHY DTO IS USED
─────────────────────────────────────────────────────────────────────────────────

  • Security: Don't expose internal entity structure to clients
  • Flexibility: Return only needed fields
  • Decoupling: Internal schema changes don't break API
  • Custom fields: Add status/message without polluting entity
  • Validation: Separate validation from persistence logic

8.3 ENTITY vs DTO IN YOUR PROJECT
─────────────────────────────────────────────────────────────────────────────────

  AgencyAcctRouting (Entity):         AgencyAcctRoutingDTO (DTO):
  ─────────────────────────           ─────────────────────────────
  - id (Long)                         - id (Long)
  - agntNbr (String)                  - agntNbr (String)
  - entpsId (String)                  - entpsId (String)
  - userId (String)                   - userId (String)
                                      - status (String)  ← EXTRA: API response status
                                      - message (String) ← EXTRA: Human-readable message

  The DTO has EXTRA fields (status, message) that are NOT in the database!
  These are response metadata for the client.

8.4 DATA FLOW
─────────────────────────────────────────────────────────────────────────────────

  CLIENT REQUEST → JSON → DTO (input)
                              ↓ ModelMapper
                          ENTITY (persistence)
                              ↓ Save to DB
                          ENTITY (response from DB)

9.1 WHAT IS JWT
─────────────────────────────────────────────────────────────────────────────────

JWT (JSON Web Token):
  A compact, URL-safe means of representing claims between two parties.
  It's a stateless authentication mechanism - the server doesn't need to
  store session data.

YOUR PROJECT: Uses nimbus-jose-jwt library (version 9.37.4) for JWT processing,
and a custom enterprise security starter (security-spring-boot-starter 3.1.7).

9.2 JWT STRUCTURE
─────────────────────────────────────────────────────────────────────────────────

  xxxxx.yyyyy.zzzzz
  HEADER.PAYLOAD.SIGNATURE

  HEADER (Algorithm & Token Type):
    {
      "alg": "RS256",
      "typ": "JWT"
    }

  PAYLOAD (Claims/Data):
    {
      "sub": "user123",
      "name": "John Doe",
      "roles": ["ADMIN"],
      "iat": 1516239022,
      "exp": 1516242622
    }

  SIGNATURE:
    HMACSHA256(
      base64UrlEncode(header) + "." + base64UrlEncode(payload),
      secret
    )

9.3 YOUR PROJECT'S AUTHENTICATION FLOW
─────────────────────────────────────────────────────────────────────────────────

NOTE: Your project uses a HEADER-BASED authentication approach (not traditional JWT
login flow). It uses enterprise SSO where the "X-User-Id" header is set by an
API gateway/proxy after the user is authenticated via enterprise SSO.

  FLOW IN YOUR PROJECT:
  1. User logs in via Enterprise SSO (outside this service)
  2. API Gateway/Proxy authenticates user
  3. Gateway sets "X-User-Id" header in request
  4. Request reaches this service with X-User-Id header
  5. UserFilter extracts X-User-Id from header
  6. Validates user exists in OV_APPLICATION_USERS table
  7. Creates SecurityContext with authenticated user
  8. Request proceeds to controller

  This is a TRUST-BASED authentication pattern common in enterprise
  microservices behind an API gateway.

9.4 WHY THIS APPROACH (Enterprise Context)
─────────────────────────────────────────────────────────────────────────────────

  • API Gateway handles JWT/OAuth2 validation
  • Internal services trust gateway's validated headers
  • Reduces auth processing in each microservice
  • Centralized authentication, distributed authorization
  • Common in Zero-Trust enterprise architectures

10.2 YOUR SECURITY CONFIGURATION ANALYSIS
─────────────────────────────────────────────────────────────────────────────────

@Configuration
@EnableWebSecurity        ← Enables Spring Security web support
@EnableMethodSecurity     ← Enables @PreAuthorize, @Secured on methods
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))  ← No HTTP sessions
            .csrf(AbstractHttpConfigurer::disable)      ← CSRF disabled (stateless API)
            .authorizeHttpRequests(auth ->
                auth.anyRequest().authenticated())      ← ALL requests need auth
            .securityContext(request ->
                request.securityContextRepository(securityContextRepository()))
            .addFilterBefore(usertFilter(),
                UsernamePasswordAuthenticationFilter.class)  ← Custom filter BEFORE default
            .build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();  ← For password hashing
    }

    @Bean
    public UserFilter usertFilter() {
        return new UserFilter();  ← Custom authentication filter
    }

    @Bean
    public SecurityContextRepository securityContextRepository() {
        return new DelegatingSecurityContextRepository(
            new RequestAttributeSecurityContextRepository(),
            new HttpSessionSecurityContextRepository());
    }
}

10.3 CONFIGURATION DECISIONS EXPLAINED
─────────────────────────────────────────────────────────────────────────────────

    → Perfect for REST APIs

  CSRF Disabled:
    → CSRF protection not needed for stateless APIs
    → No cookies/sessions to protect

  All Requests Authenticated:

    → No public endpoints (except actuator health - handled in filter)

  Custom Filter Before Default:
    addFilterBefore(userFilter, UsernamePasswordAuthenticationFilter.class)

11.1 OncePerRequestFilter
─────────────────────────────────────────────────────────────────────────────────

UserFilter extends OncePerRequestFilter:
  • Guarantees filter executes EXACTLY ONCE per request
  • Even if request is forwarded internally
  • Abstract doFilterInternal() method must be implemented

11.2 YOUR FILTER COMPLETE FLOW
─────────────────────────────────────────────────────────────────────────────────

@Component
public class UserFilter extends OncePerRequestFilter {

    @Autowired
    private UserService userService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
            HttpServletResponse response, FilterChain filterChain) {

        String url = request.getRequestURL().toString();

        // STEP 1: Check if URL is unprotected
        if (url.contains("/actuator/health") || url.contains("/favicon.ico")) {
            // Allow without authentication
            UsernamePasswordAuthenticationToken token =
                new UsernamePasswordAuthenticationToken(null, null, null);
            setDetails(request, response, token);
            filterChain.doFilter(request, response);
        } else {
            // STEP 2: Extract user ID from header
            String userId = request.getHeader("X-User-Id");

            // STEP 3: Validate user
            if (userId != null) {
                ApplicationUsers user = userService.getUserById(userId);

                if (user != null) {
                    // STEP 4: Create authentication token
                    UsernamePasswordAuthenticationToken token =
                        new UsernamePasswordAuthenticationToken(user, null, null);

                    // STEP 5: Set SecurityContext
                    setDetails(request, response, token);
                } else {
                    throw new UnauthorizedException(ERROR_UNAUTHORIZED);
                }
            } else {
                throw new UnauthorizedException(USER_NOT_FOUND);
            }

            // STEP 6: Continue filter chain
            filterChain.doFilter(request, response);
        }
    }
}

11.3 setDetails() METHOD - SETTING SECURITY CONTEXT
─────────────────────────────────────────────────────────────────────────────────

private void setDetails(HttpServletRequest request, HttpServletResponse response,
        UsernamePasswordAuthenticationToken token) {
    // 1. Add request details to token
    token.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));

    // 2. Get current security context
    SecurityContext sc = SecurityContextHolder.getContext();

    // 3. Set authentication in context
    sc.setAuthentication(token);

    // 4. Persist context
    new DelegatingSecurityContextRepository(...).saveContext(sc, request, response);
}

INTERNAL FLOW:
  SecurityContextHolder → ThreadLocal storage
  Each thread (request) has its own SecurityContext
  After filter: other Spring Security components can check
    SecurityContextHolder.getContext().getAuthentication()

Interview Answer:
  "OncePerRequestFilter guarantees single execution per request. Our custom
  filter extracts the user identity from a trusted header (set by API gateway),
  validates the user exists in our database, creates an Authentication token,
  and stores it in SecurityContextHolder's ThreadLocal SecurityContext."

13.1 YOUR GLOBAL EXCEPTION HANDLER
─────────────────────────────────────────────────────────────────────────────────

@RestControllerAdvice    ← Applies to all controllers
public class GlobalExceptionHandler {

    @ExceptionHandler(AlreadyExistException.class)
    public ResponseEntity<ErrorResponseDTO> handleAlreadyExist(AlreadyExistException ex) {
        ErrorResponseDTO error = new ErrorResponseDTO(
            LocalDateTime.now(), ex.getMessage(), "value is Already Exist");
        return ResponseEntity.status(HttpStatus.CONFLICT).body(error);
    }

    @ExceptionHandler(NotFoundException.class)
    public ResponseEntity<ErrorResponseDTO> handleNotFound(NotFoundException ex) {
        ErrorResponseDTO error = new ErrorResponseDTO(
            LocalDateTime.now(), ex.getMessage(), "value not found");
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }

    @ExceptionHandler(NoResourceFoundException.class)
    public ResponseEntity<ErrorResponseDTO> handleNoResource(NoResourceFoundException ex) {
        ErrorResponseDTO error = new ErrorResponseDTO(
            LocalDateTime.now(), ex.getMessage(), "URL not found on server");
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }

    @ExceptionHandler(Exception.class)  ← Catch-all fallback
    public ResponseEntity<ErrorResponseDTO> handleAll(Exception ex) {
        ErrorResponseDTO error = new ErrorResponseDTO(
            LocalDateTime.now(), ex.getMessage(), "Internal server error");
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(error);
    }
}

13.2 HOW @ControllerAdvice WORKS INTERNALLY
─────────────────────────────────────────────────────────────────────────────────

  1. Exception thrown in controller/service
  2. Exception propagates up the call stack
  3. ExceptionHandlerExceptionResolver intercepts
  4. Finds matching @ExceptionHandler in @ControllerAdvice classes
  5. Most specific handler wins (AlreadyExistException before Exception)
  6. Handler creates ErrorResponseDTO
  7. Returns ResponseEntity with appropriate HTTP status
  8. Client receives structured error JSON:

  {
    "timestamp": "2026-06-08T10:30:00",
    "message": "Agent number 12345 already exists",
    "details": "value is Already Exist"
  }

17.1 WHAT IS DEPENDENCY INJECTION
─────────────────────────────────────────────────────────────────────────────────

Definition:
  A design pattern where objects receive their dependencies from an external
  source (IoC container) rather than creating them internally.

Without DI:
  public class AgencyAcctRoutingController {
      private AgencyAcctRoutingService service = new AgencyAcctRoutingServiceImpl();
      // Tightly coupled! Can't mock for testing.
  }

With DI (Your Project):
  public class AgencyAcctRoutingController {
      @Autowired
      private AgencyAcctRoutingService service;  // Spring injects this!
  }

17.2 IoC CONTAINER
─────────────────────────────────────────────────────────────────────────────────

IoC (Inversion of Control):
  YOU don't control object creation → SPRING controls it.
  The ApplicationContext IS the IoC container.

  ApplicationContext contains:
  - BeanFactory (creates beans)
  - BeanDefinitionRegistry (stores bean metadata)
  - BeanPostProcessors (modify beans after creation)
  - AutowireCapableBeanFactory (resolves dependencies)

17.3 BEAN LIFECYCLE IN YOUR PROJECT
─────────────────────────────────────────────────────────────────────────────────

  1. ComponentScan finds: @Service, @Repository, @Component, @RestController
  2. BeanDefinition created for each (class, scope, dependencies)
  3. Beans instantiated in dependency order:
     - ModelMapper (no deps)
     - Repositories (depends on EntityManager)
     - UserService (depends on ApplicationUsersRepo)
     - UserFilter (depends on UserService)
     - ServiceImpl (depends on Repos, ModelMapper)
     - Controllers (depends on Services)
  4. Dependencies injected (@Autowired)
  5. @PostConstruct methods called
  6. Beans ready for use

17.4 BEAN SCOPES
─────────────────────────────────────────────────────────────────────────────────

  Singleton (DEFAULT) → One instance for entire application lifecycle
  Prototype          → New instance every time requested
  Request            → One instance per HTTP request
  Session            → One instance per HTTP session
  Application        → One instance per ServletContext

YOUR PROJECT: All beans are Singleton (default) - one controller instance,
one service instance, one repository instance serves ALL requests.

17.5 INJECTION TYPES
─────────────────────────────────────────────────────────────────────────────────

  Field Injection (Your project uses this):
    @Autowired
    private AgencyAcctRoutingService service;

  Constructor Injection (Best Practice):
    public AgencyAcctRoutingServiceImpl(AgencyAcctRoutingRepo repo, ModelMapper mapper) {
        this.repo = repo;
        this.mapper = mapper;
    }

  Setter Injection:
    @Autowired
    public void setService(AgencyAcctRoutingService service) { ... }

YOUR PROJECT: Uses both field injection (@Autowired) and constructor injection
(AgencyAcctRoutingServiceImpl has a constructor with all dependencies).

Interview Answer:
  "Constructor injection is preferred because it ensures immutability,
  makes dependencies explicit, fails fast on missing dependencies, and
  makes testing easier. Field injection hides dependencies and complicates
  testing."

    spring.datasource.hikari.idle-timeout=600000
    spring.datasource.hikari.max-lifetime=1800000

19.3 LAZY LOADING
─────────────────────────────────────────────────────────────────────────────────

  @OneToMany(fetch = FetchType.LAZY)  ← Load related entities only when accessed
  @ManyToOne(fetch = FetchType.EAGER) ← Load immediately (default for @ManyToOne)

  Lazy loading prevents N+1 query problem by not loading relationships
  until explicitly accessed.

19.4 TRANSACTION OPTIMIZATION
─────────────────────────────────────────────────────────────────────────────────

  @Transactional(readOnly = true)  ← Optimizes read operations (no dirty checking)
  @Transactional(propagation = Propagation.REQUIRES_NEW) ← New transaction
  Batch operations: spring.jpa.properties.hibernate.jdbc.batch_size=50

Q1: What is the difference between @Controller and @RestController?
A: @RestController = @Controller + @ResponseBody. @Controller returns view names
   (for MVC), while @RestController returns data directly serialized to JSON/XML.

Q2: What is Spring Boot Auto Configuration?
A: Auto-configuration automatically creates and configures beans based on
   classpath dependencies and properties. For example, if spring-boot-starter-data-jpa
   is on classpath and spring.datasource.url is set, Spring Boot auto-creates
   DataSource, EntityManagerFactory, and TransactionManager beans.

Q3: What is the purpose of @Autowired?
A: @Autowired tells Spring to inject a matching bean from the ApplicationContext
   into the annotated field/constructor/setter. Spring resolves by type, then by
   name if ambiguous.

Q4: What are HTTP status codes used in REST APIs?
A: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized,
   403 Forbidden, 404 Not Found, 409 Conflict, 500 Internal Server Error.

Q5: What is the difference between @RequestParam and @PathVariable?
A: @RequestParam extracts query parameters (/search?agntNbr=123),
   @PathVariable extracts from URL path (/agency-acct-routings/{id}).

INTERMEDIATE LEVEL
═══════════════════════════════════════════════════════════════════════════════════

Q6: Explain Spring Data JPA derived query methods.
A: Spring Data JPA generates SQL from method names at startup. Example:
   findByAgntNbrAndEntpsId(String agntNbr, String entpsId) generates:
   SELECT * FROM TABLE WHERE AGNT_NBR=? AND ENTPS_ID=?
   It parses the method name into subject, predicate, and criteria.

Q7: What is @Transactional and how does it work internally?
A: @Transactional creates a proxy around the bean. When the method is called,
   the proxy intercepts, begins a transaction, executes the method, commits
   on success, or rolls back on RuntimeException. It uses AOP (CGLIB proxy
   for classes, JDK proxy for interfaces).

Q8: What is the DTO pattern and why use it?
A: DTO decouples API contract from persistence model. Benefits: security
   (don't expose internal structure), flexibility (custom response shape),
   validation separation, and backward compatibility when schema changes.

Q9: Explain OncePerRequestFilter.
A: OncePerRequestFilter guarantees the filter executes exactly once per
   request, even if the request is forwarded/included internally. It uses
   a request attribute flag to track execution.

Q10: What is the difference between JPA and Hibernate?
A: JPA is a specification (interface/standard). Hibernate is an implementation
    of JPA. Spring Data JPA is an abstraction on top of JPA that provides
    repository pattern with auto-implemented CRUD operations.

ADVANCED LEVEL
═══════════════════════════════════════════════════════════════════════════════════

Q11: Explain Spring Security filter chain execution order.
A: Filters execute in defined order:
   SecurityContextPersistenceFilter → HeaderWriterFilter → CorsFilter →
   CsrfFilter → LogoutFilter → CustomFilter (UserFilter) →
   UsernamePasswordAuthenticationFilter → ExceptionTranslationFilter →
   AuthorizationFilter. Each filter either passes request to next or
   short-circuits with error response.

Q12: How does Spring create proxy implementations for Repository interfaces?
A: At startup, Spring scans for interfaces extending JpaRepository, creates
   JDK Dynamic Proxy using RepositoryFactorySupport. The proxy's invocation
   handler delegates to SimpleJpaRepository for standard methods, uses
   QueryExecutorMethodInterceptor for derived queries (parsed from method
   names), and JpaQueryMethod for @Query annotated methods.

Q13: Explain Hibernate first-level cache and dirty checking.
A: First-level cache (persistence context) stores entities loaded in current
   session. When transaction commits, Hibernate compares current state of all
   managed entities with their snapshot from load time (dirty checking). If
   changed, it auto-generates UPDATE SQL. This means you can modify an entity
   without calling save() - Hibernate detects and persists changes.

Q14: How does @ControllerAdvice work internally?
A: Spring registers @ControllerAdvice beans as ExceptionHandlerExceptionResolver
   advice. When a controller throws an exception, the resolver finds the most
   specific @ExceptionHandler matching the exception type, invokes it, and
   uses its return value as the response. Resolution order: same-controller
   handlers first, then @ControllerAdvice handlers sorted by @Order.

Q15: Explain how Spring resolves @Autowired dependencies with multiple candidates.
A: Spring first matches by type. If multiple beans of same type exist, it
   tries: 1) @Qualifier annotation, 2) bean name matching field name,
   3) @Primary annotated bean. If ambiguous, NoUniqueBeanDefinitionException
   is thrown.

Q16: How would you design authentication for a microservices architecture?
A: Use API Gateway pattern with centralized authentication:
   1. Gateway validates JWT/OAuth2 tokens
   2. Extracts user claims and forwards as trusted headers (like X-User-Id)
   3. Internal services trust gateway headers (your project's approach)
   4. Each service validates user exists and checks permissions locally
   5. Service-to-service uses mutual TLS or internal tokens
   6. Token refresh handled at gateway level

Q17: How would you handle the N+1 query problem in this project?
A: Identify lazy relationships causing N+1 queries. Solutions:
   1. JOIN FETCH in JPQL queries
   2. @EntityGraph annotation for dynamic eager loading
   3. @BatchSize for batch lazy loading
   4. DTO projections (SELECT new DTO(...))
   5. Avoid lazy loading in controller (use DTOs before transaction closes)

Q18: How would you make this service horizontally scalable?
A: Since it's already STATELESS (no sessions, no local state):
   1. Deploy multiple instances behind load balancer
   2. Database is shared (Oracle) - handles concurrent access
   3. Add @Cacheable with Redis for shared cache
   4. Add circuit breaker (Resilience4j) for fault tolerance
   5. Add health checks (already has actuator)
   6. Containerize with Docker, orchestrate with Kubernetes

Q19: How would you implement eventual consistency across microservices?
A: Use event-driven architecture:
   1. Publish domain events after successful operations
   2. Use Kafka/RabbitMQ for reliable event delivery
   3. Implement Saga pattern for distributed transactions
   4. Use Outbox pattern for guaranteed event publishing
   5. Idempotent consumers for at-least-once delivery

Q20: Explain your approach to designing exception handling strategy.
A: Layered exception strategy:
   1. Domain exceptions (business rule violations)
   2. Infrastructure exceptions (DB, network failures)
   3. Global @ControllerAdvice with hierarchy:
      - Business exceptions → 4xx with specific messages
      - Infrastructure exceptions → 5xx with generic messages
      - Never expose stack traces in production
   4. Correlation IDs for tracing across services
   5. Structured logging (JSON) for observability
   6. Error codes catalog for client interpretation
